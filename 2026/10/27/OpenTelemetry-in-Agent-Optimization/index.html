2026-10-27

字数统计: 6.5k   |   阅读时长≈ 28 分钟

Agent 的可观测性是一个非常重要的方向。过去一段时间，对于开发者而言，Coding Agent 的运行过程更像是一个“半透明的黑盒”——我们在终端或 IDE 里输入一句需求，看着屏幕上的工具调用和思考过程不断滚动，最后拿到代码产出。至于中间到底发起过多少次大模型请求、每次工具调用都做了什么、Subagent 是怎么运行的……往往只能去分析那晦涩的 session 文件。

2026 年 10 月 14 日，Anthropic 发布 Claude Code 2.1.300 版本，在 OpenTelemetry（OTel）中增加了 GenAI semantic-convention 信息，正式补齐了对 OpenTelemetry（OTel）的完整原生支持。

  • Added OpenTelemetry GenAI semantic-convention attributes to trace spans, such as gen_ai.provider.name, gen_ai.conversation.id, gen_ai.tool.name and error.type

在 OTel 的加持下，Claude Code 可以将每一次用户交互（interaction）、每一轮模型推理（llm_request）、每一次工具调用的三段式生命周期（tool →\rightarrow→ blocked_on_user →\rightarrow→ tool.execution）、后台异步派生的 Sub-Agent，以标准 OTLP 协议导出为完整的、结构化的 Span 调用树与事件流。

OTel 中的 GenAI semantic-convention 不仅是“多了一个看 Token 账单的监控大盘”，而是彻底改变了我们调试与优化 Agent 的工程范式：

  • Agent Trajectory 还原：我们可以像剖析分布式微服务一样，在毫秒级精度上看清多 Agent 协同中的每一步操作
  • Agent RSI(Recursive Self-Improvement)：当 Agent 执行时的所有 Trace、Log 落盘 DuckDB 后，我们可以直接让 Agent 来分析任务执行 Trace、Trajectory，并精准揪出隐形的权限审查耗时（auto_mode）、死循环排查、工具报错拦截以及编排流程中的冗余环节，形成 “任务执行 →\rightarrow→ OTel 采集 →\rightarrow→ 瓶颈归因 →\rightarrow→ Agent RSI →\rightarrow→ Trace 闭环验证” 的 Looping Engineering。

问题1：流水线缺乏“轻重分级

明明 [1] requirement-designer 在 codebase-survey.md 中已经 100% 确认“本需求仅修改 LeaderboardView.tsx:416 一行文字，后端零改动”，但流水线依然机械地启动了：

  • [4] test-case-designer（花 530s 精读 Go 源码与错误码，为完全没改动的后端接口设计了 7 条 API 用例 + 6 条重交互 E2E 用例）；
  • [5] integration-test-runner（花 364s 编译启动 Go 服务，并把 7 条 curl 拆成 7 次独立的 Bash 串行调用，每次 curl 执行仅 0.1s，但等 7 次 LLM + auto_mode 花了 85s）。

接近四成（118 次）的 LLM 请求根本不是在写代码或跑测试，而是 Claude Code 在执行 Bash 命令前调用 auto_mode 分类器判断“这条命令安不安全”！ 平均每次 auto_mode 审查都要额外阻塞 5.89 秒，累计白白烧掉了 11.6 分钟、超过 530 万缓存 Token。

为什么配了 .claude/settings.json，还会触发 118 次 auto_mode？

复合命令的“木桶效应”

Claude Code 在校验一条 Bash 命令时，会先将 Shell 命令解析为 AST 语法树，按 &&、||、;、| 拆分为多个子命令。必须每一个子命令都命中 permissions.allow，整条命令才会静态放行，只要有 1 个辅助子命令不在白名单中，整条命令就会回退给 auto_mode 分类器。

从 Trace 中可以看到 Agent 实际跑的命令：

Trace 中的实际命令（均触发了 auto_mode） 已命中的白名单项 导致穿透到 auto_mode 的未授权子命令
cd /Users/.../versus-fe && npx tsc --noEmit (seq=5) Bash(npx:*) ❌ 缺少 Bash(cd:*)（全流程有 30+ 条命令以 cd ... && 开头！）
echo "=== API-002 ===" && curl -s -m 10 ... (seq=7) Bash(curl:*) ❌ 缺少 Bash(echo:*)（导致 7 条 API-001~007 的 curl 全部触发 auto_mode）
lsof -i :9002 -i :4002 2>/dev/null | head -5; echo "---exit $?" (seq=1) Bash(lsof:*) ❌ 缺少 Bash(head:*) 和 Bash(echo:*)
sleep 8; lsof -i :9002 -P -n | head -5; tail -5 ... (seq=7) Bash(lsof:*) ❌ 缺少 Bash(sleep:*)、Bash(head:*)、Bash(tail:*)

“同义不同名”与通配符语法错位

配了 Bash(rg:*)，但 Agent 全程在用 grep（25+ 次）：settings.json 只放行了 rg，而 7 个 Subagent 的内置习惯是调 grep -rn，导致 25+ 次代码搜索全部走 auto_mode。

配了 Bash(*.sh *)，但 Agent 调的是 bash scripts/wt.sh ... 或无参 ./scripts/sync-huashu-design.sh：

  • bash scripts/wt.sh list 的首词是 bash，不匹配 *.sh *；
  • ./scripts/sync-huashu-design.sh 后面没有空格和参数，也不匹配 *.sh *（末尾带了 * 要求必须有参数）。

高频命令漏配：sed（15+ 次）、node（12+ 次）、cat、find、which、nc、mv 均未在白名单中。

漏配 Edit(**)、Write(**) 与 EnterWorktree

原配置只写了 "Read(**)"，没有写 "Edit(**)"、"Write(**)" 和 "EnterWorktree"。导致每次写 PRD.md、api-test-cases.json、run-e2e.cjs 都要走一次 auto_mode，而 EnterWorktree 更是直接弹窗阻塞了 132 秒。

3. OpenTelemetry 与 Session 文件

Claude Code 默认会在本地 ~/.claude/projects/<project>/<session-id>.jsonl 下保存完整的会话 JSONL 文件。既然这些日志也是交给分析 Agent 自动去读，为什么不直接读原始 .jsonl，而要折腾一套 OpenTelemetry 呢？

在同时对比了 .jsonl 和 OTel Trace 数据后，我发现对于 “分析 Agent 性能瓶颈与任务优化点” 而言，OTel 相比原始 .jsonl 有如下的优点：

对比维度 Claude 原始 .jsonl 会话文件 OpenTelemetry (spans + logs in DuckDB)
工具调用耗时拆解 只有发出 tool_use 和收到 tool_result 的两个离散时间戳，分不清耗时是卡在命令执行、人工弹窗审批，还是权限分类器 原生拆分为三层父子 Span：claude_code.tool →\rightarrow→ blocked_on_user（权限/人工阻塞）+ llm_request [auto_mode] + tool.execution（真正执行），毫秒级精准归因
隐形旁路 LLM 调用 完全缺失耗时与成本。例如 auto_mode 权限分类器请求不在主对话历史中，.jsonl 仅留一个 "classifierBoundary": true 布尔标记 100% 捕获。所有 query_source = "auto_mode" 的旁路推理请求均作为独立 Span 记录耗时、Token 与费用（本次靠它揪出了 118 次、695.4 秒 的隐形开销）
Subagent 关联视图 多文件碎片化。主 Agent 在 <session>.jsonl，7 个 Subagent 散落在 <session>/subagents/agent-<id>.jsonl 的 7 个独立文件里，需手动遍历对齐时间戳 全局单表视图。主从 Agent 的全部 989 个 Span 自动携带 session.id、agent_id、subagent_type 汇聚在同一张 DuckDB 表中，一条 SQL 拉出全局时间轴
分析 Agent 的 Token 开销 .jsonl 混杂了庞大的 prompt_snapshot（几十 KB 的 Tools Schema）、文件 Read 原文和 thinking，动辄数十 MB，极易撑爆分析 Agent 的 Context Window 支持 “先 SQL 聚合画像（毫秒级），再按 span_id 精准下钻读日志” 的两阶段范式，几百 Token 即可完成 70 分钟长任务的全局体检
成本与错误度量 只有原始 Token 数，无美金成本；需自行正则匹配 is_error: true api_request 事件原生计算 cost_usd；错误 Span 直接标记 status_code = 2 (ERROR)
多 Coding Agent 统一纳管 Claude Code 与 Codex 各自私有 JSONL 格式，分析脚本无法复用 遵循标准 OTLP 协议，Claude Code（service.name=claude）与 Codex（service.name=my-codex）共用同一套 DuckDB SQL 分析体系

4. OTel 的 Trace 机制

在把 7-Agent 任务导入 otel-desktop-viewer 后，我首先遇到了两个反直觉的现象：

  1. 为什么一次 /teamwork-preview 任务没有生成 1 条大 Trace，而是裂变成了 10 条独立的 Trace？
  2. 为什么同一个 session.id 下的 interaction.sequence 字段，有时候连续递增到 11，有时候又突然重置回 1？

为什么后台 Subagent 会触发多条独立 Trace？

在 Claude Code 中，Root Span 的名字叫 claude_code.interaction，它的生命周期严格对应 “主 Agent 的单次交互轮次（Turn）”，而不是整个长程业务任务。

当我们调用 Agent 工具启动一个子 Agent 时，有两种模式：

  • 前台同步模式（run_in_background: false）：主 Agent 阻塞等待子 Agent 返回，此时子 Agent 的所有 Span 会挂载在同一条 Trace 下。
  • 后台异步模式（run_in_background: true，Claude Code 默认推荐模式）：
    1. 主 Agent 调用 Agent 工具（耗时仅 10~20ms）将子 Agent 放入后台运行，随后主 Agent 向用户输出“已启动某某 Subagent”并立即结束当前 Turn（但因为后台子协程仍在运行并共享当前 Trace 上下文，子 Agent 的 claude_code.agent Span 依然挂载在当前这条 Trace 的 Root Span 下）。
    2. 当后台子 Agent 执行完毕、调用 SendMessage 交接结果时，Claude Code 会向主会话队列注入一条 <agent-message from="agent-xxx"> [Subagent hand-back] ... 消息。
    3. 这条消息会像人类输入一样重新唤醒主 Agent 开启一个新的 Turn，从而生成一条全新的 claude_code.interaction Trace，并在该新 Trace 中派生下一个流水线阶段的 Subagent！

因此，我们的 7-Agent 流水线任务（Starting at traceId = "bdc8ba25d44671bf0d6016bb9b249345"）在 OTel 中实际上是由 10 条首尾相接的关联 Trace 组成：

interaction.sequence 的重置策略

在关联同一个 session.id 下的 Trace 时，第一反应是用 interaction.sequence == 1 来判断一个新任务的开始。但反编译 claude 二进制中的 startInteractionSpan 源码后，会发现它的真实逻辑非常微妙：

也就是说，interaction.sequence 并不是按“业务任务（Task）”重置的，而是绑定在当前客户端内存进程（Host 实例）上的自增计数器：

  • 不关窗口发起新任务，序号不会置 1：比如在上面 10 条 Trace 跑完 15 分钟后，我没有关闭 VS Code 会话窗口，直接敲了一个全新的 /pull-all-repos 命令，它的 interaction.sequence 是 11。
  • 重启窗口恢复老会话（Resume Session），序号会重新置 1：因为 session.id 从磁盘恢复不变，但内存里的 lastSequence 重新从 0 开始加 1。

多 Trace 任务归并策略

在编写自动分析 Agent 时，切勿依赖 interaction.sequence == 1 切分任务，而应该按 start_time 排序后，通过识别 user_prompt 中的 <agent-message from="..."> [Subagent hand-back]、<task-notification> 以及主 Agent 处于等待审批状态后的人类确认输入（如 继续。）构建状态机，将多条 Trace 归并为一个完整的 Task Episode。

5. 数据驱动的 Coding Agent 优化

通过引入 OpenTelemetry 将 Claude Agent 的执行过程白盒化，我们不再靠“感觉哪里慢”去盲目调优，而是建立了一套从 Span 耗时拆解 →\rightarrow→ 异常拦截归因 →\rightarrow→ 规则与编排重构的 Loop Engineering。

当 Coding Agent 走向复杂的多 Agent 协同工作流时，可观测性成为 Agent 工程化的分水岭。在 OpenTelemetry 的帮助下，我们不需要手动埋点就能够让 Agent 的每一秒耗时、每一个 Token、每一次工具调用都清晰可见，优化 Agent 也像优化分布式微服务那样直观、确定且充满乐趣。
